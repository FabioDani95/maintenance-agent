# Troubleshooting Assistant
## Legacy Flask Compatibility App Specification

---

## 1. Purpose

This document describes the current behavior of the legacy `troubleshooting_agent/`
Flask application as it exists in this repository today.

Important scope note:

- the primary supported backend for this branch is `kg_agents/`
- the legacy Flask app is kept for compatibility and local standalone use
- the actual troubleshooting logic is shared from `kg_agents/engine/`

The current checked-in single-instance dataset used by the legacy app is aligned to
the **ABB IRC5** controller, not to the older Bambu Lab P1P dataset that earlier
versions of this specification described.

The application's purpose is to help a user troubleshoot a machine issue by:

1. accepting a free-text troubleshooting message
2. checking whether the message is relevant to the product domain
3. retrieving the closest known symptoms with OpenAI embeddings
4. traversing the knowledge graph from symptom to failure mode to corrective action
5. reranking candidate causes against the user's wording
6. blocking obviously unrelated causes with a no-fit guardrail
7. returning only grounded actions, sources, graph trace data, and telemetry metadata

The assistant must not invent unsupported technical procedures.

---

## 2. Design Principles

The current implementation is knowledge-grounded and mostly deterministic.

The active runtime behavior is built from:

- deterministic domain relevance checks
- embedding-based symptom retrieval
- graph traversal over the ontology
- deterministic reranking of candidate failure modes
- deterministic response rendering from retrieved graph data only

Core rule:

> The assistant must not autonomously create troubleshooting knowledge.
> It may only present causes and corrective actions supported by the ontology.

## 4. Functional Requirements

### R1. Natural-language input

The frontend sends free-text user messages to `POST /chat`.

### R2. Deterministic domain relevance check

The current implementation does not use an LLM classifier.

`domain_check.py` is a compatibility wrapper around `kg_agents.engine.domain_check`,
which performs a deterministic check based on:

- top symptom similarity score
- product metadata topics from `ontology.json`
- simple message heuristics
- likely non-English input detection

Possible outcomes:

- `relevant`
- `unclear`
- `not_relevant`

If the top symptom match is already high-confidence, the domain relevance check is
effectively bypassed.

### R3. Error code detection

The chat pipeline first checks whether the message contains an error-code-like token
matching the HMS-style pattern used by the code.

If an error code is recognized and present in the ontology:

- the app traverses `ErrorCode -> FailureMode -> CorrectiveAction`
- returns the first ranked issue immediately

If an error code is recognized syntactically but not found in the ontology:

- the app returns a fallback asking the user to also describe the symptom

Current checked-in root ontology contains `0` `ErrorCode` nodes, so this branch of
the flow is supported by the code but inactive for the default legacy dataset.

### R4. Embedding-based symptom retrieval

If no usable error code path is found:

1. the system generates a query embedding with OpenAI
2. compares it against precomputed symptom embeddings
3. returns up to `TOP_K_SYMPTOMS = 3` candidates above threshold

Current configuration:

- embedding model: `text-embedding-3-large`
- similarity threshold: `0.45`
- high-confidence threshold: `0.75`

Similarity is computed with in-memory cosine similarity using NumPy.

If no symptom exceeds the threshold, the assistant returns a low-confidence no-fit
message.

### R5. Knowledge graph traversal

For matched symptoms, `graph_traversal.py` returns paths over:

```text
Symptom -> FailureMode -> CorrectiveAction
FailureMode -> Component
```

Each returned path includes:

- symptom ID and name
- failure mode ID and name
- first affected component ID and name, if present
- action ID and name
- `instruction_text`
- `source_title`
- `source_reference`
- `related_measurements`

Duplicate `(failure_mode_id, action_id)` pairs are removed.

### R6. Deterministic reranking of candidate causes

If multiple failure modes are available, the current implementation does **not** ask
an immediate clarification question.

Instead, it reranks failure-mode groups against the current user message and returns
the top reranked issue immediately.

The reranker combines:

- matched-symptom score
- overlap between the query and failure-mode / component ontology terms
- normalized concept families such as:
  - `communication`
  - `power`
  - `input`
  - `display`
  - `software`
  - `mechanical`
  - `thermal`
- semantic similarity between the full user query and a compact text representation
  of each failure-mode group
- penalties when the query clearly points to one technical family and a candidate
  belongs to another

This reranker is deterministic once the query embedding is available.

### R7. Query-to-KG alignment guardrail

After reranking, the app checks whether the retrieved paths support explicit
technical entities named by the user.

Example of intended behavior:

- user says `ethernet`
- no retrieved path actually supports `ethernet`
- app must **not** return a joystick or unrelated power cause

If no candidate group supports the explicit technical entity named by the user, the
assistant returns a no-fit fallback instead of forcing an unrelated answer.

The guardrail is controlled by a shared engine setting:

- `QUERY_ALIGNMENT_MAX_TERM_FREQUENCY = 3`

This setting lives in `kg_agents/config.py` because the shared engine is now
defined there.

### R8. Step-through issue navigation

The issue flow is now:

1. return the first reranked issue immediately
2. store the remaining ranked issues in session state
3. expose the remaining candidates via `POST /next_issue`

Each response may include:

- `has_more_issues`
- `issue_number`
- `total_issues`

`/next_issue` iterates over the reranked order, not the raw graph insertion order.

### R9. Response rendering

`response_builder.py` is now deterministic.

It does **not** call an LLM to generate prose. Instead it formats grouped graph data
into a grounded markdown response containing:

- the selected failure mode
- the affected component, if present
- all unique corrective actions for that failure mode
- source citations for those actions

The configured `OPENAI_CHAT_MODEL = gpt-5-mini` is still present in config and API
payloads for compatibility, but the current legacy app behavior does not depend on
chat-completion calls.

### R10. Source citation behavior

Two source modes are supported:

1. URL source
   - if `source_reference` starts with `http`, the response uses a web link
2. Manual source
   - if `source_reference` contains or is a numeric page reference, the response
     emits a marker of the form:
     `[MANUAL:<source_title>:<page>]`

The frontend converts the manual marker into a UI action that opens the local PDF.

### R11. Graph highlighting

The backend builds a trace containing:

- `symptom_ids`
- `error_code_ids`
- `failure_mode_ids`
- `action_ids`
- `component_ids`
- `edges`
- `scores`
- `reasoning`

This trace is returned by `/chat` and `/next_issue` and is consumed by the frontend
to highlight the active troubleshooting path.

### R12. Telemetry support

If the active failure mode exposes `related_measurements`, the backend attempts to
load:

- time series via `get_signals()`
- summary statistics via `get_stats()`

Telemetry is optional:

- missing CSV files do not crash the app
- unknown columns are skipped
- telemetry may be absent in the response

### R13. Session reset

`POST /reset` clears the in-memory troubleshooting session for a given `session_id`.

### R14. Server lifecycle

`agent.py` currently provides:

- stale-port cleanup using `lsof`
- ontology load validation on startup
- embedding coverage validation for all ontology symptoms
- browser auto-open
- graceful exit on `SIGINT` and `SIGTERM`

## 5. Architecture

```text
Browser UI
  -> GET /                     frontend_routes.py
  -> POST /chat               api_routes.py -> orchestrator.py
  -> POST /next_issue         api_routes.py -> orchestrator.py
  -> POST /reset              api_routes.py
  -> GET /graph_data          api_routes.py
  -> GET /product_info        api_routes.py
  -> GET /status              api_routes.py
  -> GET /manuals/<filename>  api_routes.py
  -> GET /telemetry/<signal>  api_routes.py

orchestrator.py
  -> domain_check.py          compatibility wrapper
  -> embeddings.py            compatibility wrapper
  -> similarity.py            compatibility wrapper
  -> graph_traversal.py       compatibility wrapper
  -> response_builder.py      compatibility wrapper
  -> telemetry_loader.py      compatibility wrapper
  -> ontology_loader.py       compatibility wrapper
  -> shared implementation in kg_agents/engine/*
```

Application composition:

- `app_factory.py` creates the Flask app and registers blueprints
- `frontend_routes.py` serves the HTML shell
- `api_routes.py` serves JSON and manual endpoints
- `routes.py` keeps `app = create_app()` for compatibility
- most troubleshooting logic now lives in `kg_agents/engine/`

## 6. API Surface

| Method | Path | Description |
|---|---|---|
| `GET` | `/` | Main web UI |
| `POST` | `/chat` | Submit user message and receive reply, trace, issue metadata, optional telemetry |
| `POST` | `/next_issue` | Move to the next reranked issue in the current session |
| `POST` | `/reset` | Clear session state |
| `GET` | `/graph_data` | Full ontology as vis-network payload |
| `GET` | `/product_info` | Product metadata plus suggested symptoms |
| `GET` | `/status` | Ontology status summary |
| `GET` | `/manuals/<filename>` | Serve local manual PDFs |
| `GET` | `/telemetry/<signal_name>` | Return raw series and statistics for one telemetry signal |

Current `POST /chat` and `POST /next_issue` responses may include:

- `reply`
- `session_id`
- `highlight`
- `has_more_issues`
- `issue_number`
- `total_issues`
- optional `telemetry`

Unlike the primary `kg_agents` API, the legacy Flask app does not expose:

- structured `current_issue`
- intervention outcome logging
- path statistics
- the newer `Resolved` / `not_resolved` workflow

## 8. Data Dependencies and Assumptions

The current implementation assumes:

- root `ontology.json` is valid and consistent with the expected traversal fields
- `troubleshooting_agent/symptom_embeddings.json` contains an embedding for every ontology symptom
- local manuals referenced by `source_title` exist in `troubleshooting_agent/manuals/`
- manual references are either URLs or parseable page references
- telemetry column names referenced in `related_measurements` exist in the configured CSV when telemetry is used

Startup behavior:

- missing symptom embeddings for ontology symptoms cause startup failure
- extra stale embeddings only produce a warning
- missing telemetry data degrades gracefully

Telemetry note:

- the default telemetry path still points to
  `troubleshooting_agent/telemetry/telemetry_p1p.csv`
- this filename is historical and does not imply that the active ontology is still P1P
- the telemetry loader itself is generic and only depends on column availability

## 9. Procedure for Re-instantiating the Legacy App for Another Product

The legacy app can be reused for another product only if the new ontology still
respects the runtime assumptions of the shared engine.

### 9.1 Minimum data contract to preserve

To keep the current code working without changes, preserve:

- top-level sections: `metadata`, `nodes`, `relationships`
- node classes required by troubleshooting:
  - `Symptom`
  - `FailureMode`
  - `CorrectiveAction`
  - optional `Component`
  - optional `ErrorCode`
- operative relationships:
  - `MAY_INDICATE`
  - `RESOLVED_BY`
  - `AFFECTS`
  - optional `INDICATES`
- ID fields used by traversal and rendering:
  - `symptom_id`
  - `failure_mode_id`
  - `action_id`
  - optional `component_id`
  - optional `error_code_id`

### 9.2 Metadata that should be updated

When changing product, update at least:

- `product_name`
- `product_short_name`
- `product_type`
- `domain_topics`
- `version`
- `total_nodes`
- `total_relationships`

This matters because product metadata is used by:

- domain relevance heuristics
- fallback messages
- `/product_info`
- `/status`

### 9.3 Symptom embeddings must be regenerated

If `Symptom` nodes are changed, added, removed, or renamed, regenerate the symptom
embedding file:

```bash
PYTHONPATH=. python3 troubleshooting_agent/embeddings.py
```

This is mandatory because:

- retrieval depends on `symptom_embeddings.json`
- `agent.py` validates that every ontology symptom has an embedding
- missing embeddings block startup

### 9.4 Corrective action source requirements

For each `CorrectiveAction`, the runtime expects:

- `instruction_text`
- `source_title`
- `source_reference`

Source handling rules:

- web URLs are rendered as links
- numeric or parseable page references are rendered as manual markers

If local manuals are used for the new product:

- place them in `troubleshooting_agent/manuals/`
- make `source_title` align with the manual naming expected by the frontend flow

### 9.5 Telemetry alignment

Telemetry is optional, but if used:

- `FailureMode.related_measurements` must list valid signal names
- those names must exist in the configured CSV

If telemetry is not needed, omit `related_measurements` and the app still works.

### 9.6 Cases that require code changes

The following changes cannot be handled by ontology replacement alone:

- replacing the traversal entry point with something other than `Symptom`
- removing or renaming the relation types used in traversal
- removing or renaming the ID fields used by the engine
- changing how sources or manuals are represented
- changing telemetry storage away from the current wide CSV model
- changing the troubleshooting flow to a clarification-first dialogue

The primary modules impacted in that case would be the shared engine modules under:

- `kg_agents/engine/ontology_loader.py`
- `kg_agents/engine/graph_traversal.py`
- `kg_agents/engine/embeddings.py`
- `kg_agents/engine/query_alignment.py`
- `kg_agents/engine/response_builder.py`

and the legacy transport layer:

- `troubleshooting_agent/api_routes.py`
- `troubleshooting_agent/orchestrator.py`
- `troubleshooting_agent/static/js/app.js`

### 9.7 Recommended migration checklist

1. Replace root `ontology.json` with the new product instance.
2. Update ontology metadata for the new product.
3. Verify required node classes, IDs, and relationship names.
4. Update or add local manuals if manual citations are used.
5. Update telemetry data and `related_measurements` if telemetry is required.
6. Regenerate `troubleshooting_agent/symptom_embeddings.json`.
7. Start the app with `PYTHONPATH=. python3 troubleshooting_agent/agent.py`.
8. Validate:
   - startup passes embedding checks
   - `/product_info` shows the new product metadata
   - `/graph_data` renders correctly
   - `/chat` retrieves valid troubleshooting paths
   - `/next_issue` iterates through the reranked candidate causes
   - manuals and telemetry still render when present

## 10. Explicit Non-Goals of the Current Legacy App

The current legacy Flask app does **not** implement:

- LLM-based domain classification
- LLM-based answer generation
- an immediate clarification-question turn before returning the first cause
- intervention outcome logging
- structured action selection payloads
- path statistics

Those behaviors were described in older documents but are not accurate for the
current repository state.

## 11. Repository Alignment Notes

This specification supersedes older descriptions that referenced:

- **Bambu Lab P1P** as the active legacy dataset
- LLM-based classification or LLM-based answer formatting
- a clarification flow that asks one question before returning the first cause
- ranking by keyword overlap with the clarification answer
- the old assumption that the legacy app owned its own engine implementation

For the current repository state:

- `kg_agents` is the primary supported backend
- `troubleshooting_agent` is a compatibility app
- the shared engine in `kg_agents/engine/` defines the actual troubleshooting logic
